# 批次采集 spec

状态：本 spec 已获用户批准，实施版本 v0.2.0 已合入 main，原实施基线为 v0.1.4。用户在具体版本、验证与独立审查结果汇报后，明确接受本轮模拟验收范围并批准合入、归档及清理，现已完成。原验收条件保留，未完成的真实浏览器验证及收尾证据见 [status.md](status.md)。

## 1. 目标与范围

用户在后台系统中手动切换业务页签、查询、筛选和翻页。工具持续记录本批接口，每次由用户保存当前页面画面和接口增量，减少反复刷新、截图和手动整理文件的操作。

- 一批绑定开始时的浏览器标签页，同时只支持一个活动批次。网页地址、业务页签及 iframe 内部切页不触发自动分批；其他浏览器标签页不自动并入。
- 用户通过现有扩展小面板或 Alt+Shift+Y 打开操作入口，备注选填。记录生命周期独立于备注面板，关闭面板不停止记录。
- 继续采用本地 Chromium Manifest V3 扩展。目标机器无需 Node.js、服务器或 F12，不增加业务自动操作、外部上传或采集结果压缩。

术语见仓库根目录 [GLOSSARY.md](../../../GLOSSARY.md)。本 spec 经用户批准后作为实施基线；README 继续描述当前已发布版本。

## 2. 用户流程与输出

1. 用户在业务页点击“开始本批”。先连接并开启网络记录，再自动刷新一次；等待加载和短时请求后自动保存 001。首份准备沿用约 2.6 秒空闲、最多 20 秒的等待上限，超时说明不完整。该上限只约束首份准备，不自动结束整批。
2. 用户继续操作业务页。每次点击“保存一次”，保存当前整页截图、选填备注和本次接口增量，随后继续记录；不再刷新、不另起批次。
3. 用户点击“结束本批”。有剩余接口时补存最后一份，没有剩余且没有未完成请求时直接结束。
4. 终态保留“关闭并返回原页面”。本批正常结束或明确放弃后才能开始下一批；新批首次采集再自动刷新一次。

每批目录在开始时确定，后续页面标题或地址变化不改变目录。每份使用递增的序号子目录，正常包含：

```text
PageCapture/批次标识/
  001/page.json
  001/screenshot-full.png
  001/note.txt
  002/同样三个文件
```

page.json 顶层始终为数组，每项只有 request、response。没有新接口时也允许用户主动保存，JSON 为 []。元信息、备注、实际截图范围、正文省略原因、未完成请求、覆盖限制和异常原因均写入 note.txt。

## 3. 增量边界与等待

- 接口增量按“本批尚未成功留档的请求记录”计算，不能仅按 URL 去重或按请求发起时间截断。相同接口的多次调用分别保留；上次超时、这次才返回的请求必须进入后续快照。
- 普通保存时确定本次等待的请求集合，最多等待 5 秒收齐这些请求的结果，再截图、冻结导出数据。操作开始后新发起的请求继续记录，留给下一份，不延长本次等待。首份自动保存采用第 2 节的首次准备上限。
- 超时仍未完成的请求不作为本次已保存记录提交，继续跟踪，返回后归入下一份。本份备注记录仍有未完成请求。
- 请求的网络失败也属于可留档结果，在诊断中说明。请求完成但正文不可得时，保留请求与响应元数据，按现有省略规则说明原因。
- 截图反映画面截取时已渲染的状态。工具不暂停业务脚本，不把截图和网络记录宣称为严格原子快照。

结束本批时，截止集合为用户点击结束前已经纳入记录的请求；后续新请求不并入，但不拦截业务网络。最多等待 20 秒收齐截止集合。仍未返回的保留已有请求信息，明确缺少返回，不伪造响应成功，然后完成末份留档。

## 4. 保存成功、重试与缺图

- 一次只允许一个快照保存操作。准备完成后冻结该份截图、接口数据、备注、目录和序号，下载期间不再把新请求加入该份。
- 正常快照必须等浏览器报告三个文件下载完成，才提交本份记录为已保存、推进增量边界。仅发起下载不算成功。
- 部分下载失败时保留原快照，只重试失败文件；已完成文件不主动重复下载。重试沿用同一逻辑快照和目录，不生成新序号，不用重试时的页面画面替换原截图。
- 等待重试期间，普通记录继续进行，但禁止新建下一份或正常结束。提供“放弃未保存数据并结束”，执行前说明影响，不删除已经下载的文件。
- 整页截图失败先回退当前视口，备注说明实际范围。连视口截图也失败时，冻结为缺图快照：JSON 与备注均下载完成即视为该份接口已留档，推进增量边界；界面明确显示“接口已保存，截图失败”，不显示完整成功。
- 结束过程中的末份下载失败也必须重试或明确放弃。重试不重新开启请求收集，不移动结束截止集合。

## 5. 状态与中断

| 状态 | 允许的主要操作与转移 |
| --- | --- |
| 未开始 | 开始本批，随后进入首次准备 |
| 首次准备 | 记录、刷新、自动保存首份；防止重复启动 |
| 记录中 | 保存一次或结束本批 |
| 保存中 | 普通保存持续记录；禁止重复保存；普通保存成功回到记录中，末份保存成功进入已结束，失败进入等待重试 |
| 等待重试 | 重试失败文件或明确放弃；保持原快照与结束意图 |
| 结束中 | 截止新请求，等待已有请求，必要时保存末份 |
| 已中断 | 不自动重连或刷新；补导出已有数据、重试失败快照或明确放弃 |
| 已结束 | 关闭并返回原页面，允许开始下一批 |

业务页关闭、调试连接断开等情况必须停止继续收集并显示具体原因。记录宿主仍在时，保留已收到的数据供补导出；业务页已经不存在时可以按缺图规则留档。

技术落地建议：优先复用一个贯穿整批的扩展状态页作为记录宿主，普通小面板只负责操作和展示状态；每次保存不再创建新状态页。这样保持现有最低内核的基础兼容。状态页需保持打开，记录中不能把“关闭并返回”当作普通收起入口。若记录宿主被关闭、浏览器退出或扩展重载，未保存缓存不保证恢复；已下载文件保留。本轮不实现跨重启恢复。

## 6. 接口范围、兼容与资源

- 保留现有 Fetch/XHR 范围和实际 HTTP 方法，排除可识别的扩展请求及关联预检。保持认证字段脱敏、JSON/表单处理、multipart 省略、业务原有字段保留等行为。
- 复用现有调试连接、下载和截图能力。新增批次调度、不可变快照及文件完成状态，监听和缓存均不能依附短暂的小面板；不新增浏览器权限。
- 每条内部请求需按根标签、子会话及重定向段区分，防止不同 iframe 的请求标识碰撞。多层子页面分别建立监听，导航后更新子页面生命周期；URL 变化不重置未保存增量。
- 最低声明保持 Chrome 105。Chrome 125 及以上补齐并测试跨进程 iframe 子会话；旧内核保留基础采集，无法确认的覆盖限制在界面和备注中说明。子页面监听失败或途中断开不得显示完整成功。
- 整页截图不主动展开内部滚动容器，不触发未渲染懒加载；不能保证包含这些区域的隐藏内容。
- 保留单条正文 2 MiB、未成功留档正文累计 24 MiB 的上限，超限记录省略原因。成功留档后释放对应正文和截图缓存；保留重试快照和未保存增量。元数据缓存也必须有明确上限，达到资源上限时提示不完整并停止继续收集，保留可补导出的数据；实现时记录上限及触发验证。

## 7. 验收与验证

优先从“用户发出开始、保存、重试、结束命令，最终得到哪些下载文件及状态”的整体边界验证，复用现有 Node VM 和模拟 Chrome API 的测试基础。模拟测试使用可控时钟、合成请求和下载事件，不把私有函数名或内部分组方式当作主要断言。

| 场景 | 必须观察到的结果 |
| --- | --- |
| 开始本批 | 监听先于唯一一次刷新；自动生成 001，之后仍可记录 |
| 连续保存三次 | 每次截图为对应状态；各目录仅包含各自未保存增量，已保存记录不重复 |
| 同接口多次调用 | 分类、筛选和翻页的不同调用分别保留，实际方法不变 |
| 没有新请求 | 主动保存仍产生截图、[] 和备注，不结束批次 |
| 慢请求与保存期间的新请求 | 保存最多等 5 秒；迟到结果及新请求进入下一份，无静默丢失 |
| 单文件失败及重复点击 | 不推进边界、不重截原画面；仅重试失败文件，成功后继续；无并发重复快照 |
| 结束与未完成请求 | 无剩余时不生成空末份；有剩余补存；最多等待 20 秒并明确未返回情况 |
| 末份失败与主动放弃 | 正常结束被阻止；可重试或明确放弃，已下载文件保留 |
| 整页失败及完全缺图 | 分别显示视口回退与缺图状态；缺图仅在 JSON、备注完成后提交 |
| 页面切换、iframe 与标识碰撞 | 批次和目录保持，子会话独立识别；覆盖不足有可见诊断 |
| 面板关闭、连接中断 | 关闭备注面板继续记录；中断不自动刷新，可补导出已收到数据 |
| 脱敏与资源上限 | 保持现有过滤及数据结构，省略原因入备注；缓存释放与触限停止可验证 |

实施完成后运行项目的 npm test、npm run check、npm run package，并校验打包内容及版本一致。真实浏览器以本机可用 Edge/Chromium 验证首次刷新、业务页签切换、筛选翻页、连续留档、失败提示及返回原页；合成页面覆盖 iframe 与内部滚动布局。不得自动安装新浏览器。旧内核、客户内网浏览器和实际客户嵌套页面未实测时必须明确记录，VM 通过不代表这些环境通过。

## 8. 不包含与审批

不包含自动遍历或翻页、重放业务请求、创建或修改业务记录、全浏览器后台监听、跨标签自动合并、跨重启恢复、WebSocket/SSE 消息帧、商店发布和外部数据上传。真实 HAR、截图、接口返回、备注和客户地址仍保留在仓库外，测试只用合成资料。

本 spec 不拆票。实施与收尾遵循用户已给出的授权：完成验证和独立审查，汇报最终版本及未验证范围后，合入 main、归档并按 Git worktree 原入口清理本任务资源。
